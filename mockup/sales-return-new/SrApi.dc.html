Step 3 · Backend API and phone data changes

Server side in the ERP server mobile module, calling the desktop sale-return service so the rules stay in one place. Written for the recommended decisions.

VK Nex today

  • No phone return route: src/mobile-modules/ has order, visit, bill, receipt only, and MobileUploadKind has no return kind.
  • sale_return has no client-uuid column; a resend is safe only by sending the same srId.
  • srCounterId is required on create (SALES_FIELD_REQUIRED); a phone has no counter.
  • No skip-right option: /post needs the Post right on menu 13. WARN codes block /post unless overridden.
  • No route lists a customer's bills for returns; GET /sale-returns/bill-lines reads one bill.

GET /mobile/returns/options

NEW

At Sync, per company and branch.

  • reasons[]: srmId, code, name, defaultCondition, refundCharges, isClaim (SALE_RETURN reasons; claim ones flagged so the phone hides them).
  • settings: returnWindowDays, freeReturnAllowed, settleDefault, expiredLotDays, roundOffStep.
  • godowns[] of the branch with the default marked; rights on menu 13 (create, post).

GET /mobile/returns/bill-lines

NEW

At Sync, paged: the posted bills of the company's customers for the last [90] days (or the return window), built with sale-return-bill-reader so the figures match the desktop's.

  • bills[]: sbId, accYear, refno, date, custId, billAmount, due, payMode, returnedAmt, returnStatus, branchId.
  • lines[]: billItemId, accYear, lineNo, itemId, itemUnitId, toBaseFactor, units[], billQtyBase, returnedQtyBase (posted), qtyLeftBase, onOtherDraftsBase, taxable per base unit, GST % split, lotId, batchNo, expiryDate, godownId, isFree, allowReturn.
  • Fully returned bills are sent too (the "Show fully returned" tick).

POST /mobile/returns/create

NEW

One call: save the draft, then post it. Same pattern as mobile-bill.service.ts: lockMobileClientUuid, a duplicate answers the stored result, another customer on the same uuid answers MOBILE_CLIENT_UUID_REUSED.

  • Body: srClientUuid (also srId), srMobileRefno, srCompanyId, srBranchId, srCustId, srIsAgainstBill, srBillId / srBillAccYear, srReasonId, srSettleMode (ADJUST | ADVANCE), srReturnDate, srUsrRefno / srUsrRefdate, srRemarks, godownId, adjustments[] (optional), phoneEstimate (info only).
  • Lines: sriBillItemId, sriBillAccYear, sriItemId, sriItemUnitId, sriReturnQty, sriCondition, sriSplitNo, sriRemarks; no-bill lines add sriBatchNo, sriExpiryDate. No money keys.
  • VK Nex fills device, counter, acc year, user and salesmen (from the bill, else the login's employee), checks the godown is the branch's (MOBILE_GODOWN_INVALID), creates the DRAFT (SRT number) and posts in a SAVEPOINT with origin PHONE.
  • Post refused for the office (428 approval, a WARN code, 403 Post right) → keep the DRAFT, answer status: "HELD" + heldFor {code, message}.
  • Post refused by a rule (e.g. SALES_RETURN_OVER_QTY) → keep the DRAFT, answer status: "SENT_BACK" + refusal {code, field, line, message}. A resend with the same uuid re-saves that draft and posts again.
  • Answer: srId, srReturnRefno, status (POSTED | HELD | SENT_BACK), srReturnAmt, settlement {adjusted[{refno, amount}], credited}, lines[{sriId, rate, taxable, tax, net, bucket}], warnings[].

POST /mobile/returns/delete

NEW

{ srClientUuid } — deletes a HELD or SENT_BACK draft when the salesman deletes it on the phone. A posted return answers SALES_DOC_POSTED (office only).

GET /mobile/returns/status

NEW

At each Sync, ?companyId&since: returns of this device changed since then.

  • srClientUuid, srId, srReturnRefno, status DRAFT | POSTED | CANCELLED, approval PENDING | APPROVED | REJECTED (+ note), revisionNo, srReturnAmt, settleStatus, adjusted bills, asOf.

Reused as they are

REUSE
  • GET /mobile/me — the login's employee for a no-bill return.
  • GET /mobile/receipts/open-bills?withCredits=true — read after the returns upload, so adjusted bills and held credits are current on Receipt.

VK Nex: data and service changes

  • Migration: sales.sale_return + sr_client_uuid uuid (unique per company) and sr_mobile_refno varchar(30).
  • MobileUploadKind gains 'return'; a phone counter for srCounterId (question 1).
  • Post option { origin: 'PHONE', replanStaleAdjust: true }: a stale adjust row moves to the next oldest bill or stays as credit (decision 6). No skip-right: a phone without the Post right gets a HELD draft (decision 7).
  • Error_Messages rows for the new codes (MOBILE_RETURN_HELD and the re-plan warning); wording to be checked by the user.

Phone: data, Sync and screens

  • sale_return: add sr_bill_id, sr_bill_acc_year, sr_reason_id, sr_return_reason, sr_godown_id, sr_usr_refno, sr_usr_refdate, sr_remarks, app_status (WAITING | HELD | SENT_BACK | POSTED | CANCELLED), app_vk_refno, app_vk_amt, app_vk_note; settle mode ADJUST | ADVANCE.
  • sale_return_item: add sri_bill_item_id, sri_bill_acc_year, sri_split_no; condition gets RESTOCK and SCRAP; price stays only as the estimate.
  • New download tables: return_bills, return_bill_lines, return_reasons; return settings and branch godowns in device_meta.
  • Sync order: customers → orders → bills → returns → receipts → visits, then open-bills, return bill-lines and return status.
  • Screens: the 4 routes under src/app/sales-return/ become the 11 screens here; a Return list tile on Customer detail; Return goods on Visit.
